# Phase 0 Research: Employee Self-Service Salary Access

No items in Technical Context were marked `NEEDS CLARIFICATION` — this feature reuses existing, already-proven patterns end to end. This document records the decisions made and why, for traceability.

## Decision 1: Each new endpoint gets its own use case and repository (no cross-slice reuse of either)

- **Decision**: `get_my_salary_summary/` and `list_my_salary_advances/` each define their own `application/use_case.py` (`GetMySalarySummary`, `ListMyAdvances`) and own `infra/repository.py` (`GetMySalarySummaryRepository`, `ListMyAdvancesRepository`). Neither imports `GetSalarySummary`, `GetSalarySummaryRepository`, `ListSalaryAdvances`, or `ListSalaryAdvancesRepository` from the HR-facing slices.
- **Rationale**: This codebase already has the exact precedent for this situation — `list_my_journeys` (self-service) sits alongside `admin_list_journeys` (admin-facing over any user), and despite querying the same `JourneyRegistry` table with nearly the same filter, `list_my_journeys` has its own `ListMyJourneysRepository.list_by_user(user_id)` rather than importing `AdminListJourneysRepository`. Vertical Slice Architecture (Constitution I) requires every feature to be a *self-contained* slice; importing another feature's use case/repository class makes that slice's business logic and persistence behavior implicitly dependent on a different feature's implementation, which is exactly what the architecture is meant to prevent — a change made to satisfy the HR-facing feature (e.g. changing its query shape, error handling, or return type) would silently ripple into the self-service feature.
- **What *is* reused instead**: the pure, stateless functions in `get_salary_summary/domain/rules.py` (`calculate_daily_delay_minutes`, `is_late`, `calculate_deduction`) — mirroring the already-established precedent of `update_loan/application/use_case.py` importing `validate_amount_dates`/`calculate_total_amount` from `create_loan/domain/rules.py`. Domain-layer pure-function reuse across sibling slices is a distinct, already-accepted pattern in this codebase — separate from, and not an exception to, the "no cross-slice use case/repository reuse" rule.
- **Cost accepted**: `GetMySalarySummaryRepository` duplicates `GetSalarySummaryRepository`'s employee/advances lookup, lateness-configuration fetch, and journey-timestamp query almost verbatim, and `ListMyAdvancesRepository` duplicates `ListSalaryAdvancesRepository`'s filter logic (minus the cross-employee `employee_id` parameter). This is accepted duplication, consistent with `list_my_journeys` doing the same today, and with this project's own stated preference for duplication over premature abstraction.
- **Alternatives considered**:
  - *Import and call the existing `GetSalarySummary`/`ListSalaryAdvances` classes directly* (the initial plan draft): rejected after review — this is a cross-slice use-case/repository dependency that the codebase's own `list_my_journeys`/`admin_list_journeys` precedent explicitly does not do, and it violates the "feature use cases aren't reusable" reading of Constitution I.
  - *Branch inside the existing HR routes* (`if employee_id is None: employee_id = current_user.employee.id`): rejected — would interleave two different permission models (`ensure_hr` + arbitrary employee vs. `ensure_employee` + self-only) in one route function, and would change the existing HR endpoints' contract, which the standing API contract (`specs/api/employees.md`) says must only change when the route itself changes.
  - *Extract a shared, non-slice-owned service class for both slices to call*: rejected — introduces a new architectural abstraction (a "service" layer outside any slice's `application/`) not used anywhere else in this codebase, contradicting Constitution IV (Consistency Over Cleverness).

## Decision 2: Identity resolution — how `employee_id` is derived for `/me` routes

- **Decision**: `current_user.employee` (the existing reverse one-to-one relation from `User`, already eagerly loaded via `prefetch_related("roles","employee")` in `get_current_user`) supplies the `Employee` row; its `.id` is passed as `employee_id` into the reused use cases. If `current_user.employee` is `None`, the route rejects the request before calling the use case.
- **Rationale**: `prefetch_related("employee")` was already added to `app/shared/security/current_user.py` on the current branch (uncommitted, unused) — this feature is the consumer that groundwork was laid for. No new query or dependency is needed; the relation is already resolved by the time the route body runs.
- **Alternatives considered**: Adding a separate DB lookup (`Employee.get_or_none(user_id=current_user.id)`) inside each new route — rejected as redundant, since the same data is already attached to `current_user` for free.

## Decision 3: Route registration order

- **Decision**: The two new routers (`/employees/me/salary-summary`, `/employees/me/salary-advances`) are registered in `app/slices/employees/urls.py` in the fixed-prefix block, before the dynamic `get_employee_router` (`GET /employees/{employee_id}`).
- **Rationale**: `employee_id` on `get_employee`'s route is declared as a plain `UUID`-typed function parameter without an explicit path convertor, so Starlette's router matches `/employees/me` against `/employees/{employee_id}` at the string-routing level (any non-slash segment matches), and only fails afterward during FastAPI's parameter parsing — which does not fall through to a later-registered fixed route. This exact hazard is already called out by an existing comment in `urls.py` for `/salary-advances` and `/lateness-config`; the same rule applies to `/me`.
- **Alternatives considered**: None — this is a hard routing-order requirement, not a preference.

## Decision 4: Response schema reuse across slices (distinct from the use-case/repository rule)

- **Decision**: `get_my_salary_summary/ui/schemas.py` and `list_my_salary_advances/ui/schemas.py` import the existing `SalarySummaryResponse` and `SalaryAdvanceItem` models from the HR-facing slices rather than redefining field-identical copies.
- **Rationale**: Cross-slice `ui/schemas.py` reuse is already established practice in this codebase — `list_my_journeys/ui/route.py` imports `JourneyResponse` from `register_journey`, and `update_loan/ui/route.py` imports `LoanResponse` from `create_loan`. This is a narrower, HTTP-contract-only form of sharing than reusing a use case or repository: schemas carry no behavior, so importing one doesn't create the same implicit coupling to another feature's business logic or persistence behavior that Decision 1 rejects for use cases/repositories.
- **Alternatives considered**: Defining separate, field-identical `MySalarySummaryResponse`/`MySalaryAdvanceItem` models — considered, but rejected as pure duplication with no independence benefit, since nothing in this feature's requirements calls for the self-service shape to ever diverge from the HR-facing one; if that need arises later, splitting the schema at that point is a small, contained change.

## Decision 5: Lateness detail visibility for self-service (spec FR-008)

- **Decision**: `GetMySalarySummary`'s return value (and therefore the `SalarySummaryResponse` it populates) includes `late_delay_minutes`, `late_days_count`, and `late_deduction_total` — the same lateness fields HR already sees.
- **Rationale**: Already decided at the spec level (FR-008 and Assumptions in `spec.md`). Technically, this only requires `GetMySalarySummaryRepository`/`GetMySalarySummary` to perform the same lateness-configuration lookup and delay/deduction calculation that `GetSalarySummary` already performs (via the reused `domain/rules.py` functions, per Decision 1) — there is no code path that would need to strip these fields.
- **Alternatives considered**: N/A — this was a spec-level decision, not a technical one.
